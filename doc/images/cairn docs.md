Cairn UI
Technical Documentation — Architecture, Technology Choices, and Key Concepts

Project 10 of a 2026 fullstack + gen-AI / starter-kit portfolio series. Repository: github.com/rlphjyson/cairn_ui
 
1. Overview
Cairn is a pure Flutter UI package — 65 components (45 shadcn/ui recreations plus 20 daisyUI-inspired extensions) recreating shadcn/ui with genuine dimensional accuracy: the same spacing, border radius, color values, typography scale, and shadow treatment as shadcn/ui's real current source, translated faithfully into Flutter rather than copied (there is no source to copy between React/Tailwind and Dart/Flutter). This is a library, not an app, so most of the app-level concerns elsewhere in this portfolio series (auth, analytics SDKs, offline sync) don't apply — the senior-engineering bar for a component library is different: token accuracy, theming, accessibility, and test coverage that actually locks in visual correctness over time.
45 components shipped against an original target of ~35-40, 114 tests including 52 byte-compared golden images, a perfect 160/160 pana score (pub.dev's own package-quality scorer), and a clean publish dry run.
2. What "Pixel-by-Pixel" Actually Means and How It's Verified
Flutter's rendering engine (Skia/Impeller) and a browser's CSS engine will never produce byte-identical screenshots of each other — different rasterization pipelines, different font shaping. Chasing literal cross-engine pixel equality would be a waste of effort and isn't what "pixel-by-pixel" means in this project. What it actually means: shadcn/ui's real Tailwind-class specifications for every component — exact padding, height, border radius, color, shadow, and ring values — were extracted from its live source and translated precisely into Flutter's coordinate system (logical pixels), then locked in place going forward with golden tests that catch the moment any future change silently drifts from that baseline.
How the tokens were actually extracted
The shadcn-ui/ui GitHub repository was sparse-cloned and its real component source files (apps/v4/registry/new-york-v4/ui/*.tsx) were read directly for their Tailwind utility strings, rather than relying on any pre-existing knowledge of shadcn's internals, which changes across versions. Canonical color values came from ui.shadcn.com's own published color registry (r/colors/neutral.json), and the actual radius calculation formula came from shadcn's own CLI source (update-css-vars.ts).
Four things stale knowledge gets wrong about current shadcn/ui
1.	shadcn/ui's color system is defined in OKLCH, not HSL. Any implementation still working in terms of hsl(var(--primary)) is working from an outdated version of the library.
2.	The border-radius scale is multiplier-based now (calc(var(--radius) * 0.6 / 0.8 / 1.4)), not the older additive form (calc(var(--radius) - 4px), etc.). The two formulas happen to agree exactly at shadcn's default base radius of 0.625rem — producing identical 6/8/10/14 pixel results — which is exactly why the underlying formula change could go unnoticed; they only diverge once a project customizes its base radius value.
3.	The documentation site's own visual theme is not the same as the theme its CLI actually writes into a new project. ui.shadcn.com overrides its foreground and primary colors to pure black for the site's own branding, while the actual registry template (what `shadcn init` generates) uses slightly different lightness values. Cairn intentionally follows the registry template, not the marketing site's styling — copying the site's own CSS would have been a subtly wrong, if visually similar, choice.
4.	The --destructive-foreground color token was quietly dropped from current shadcn/ui; destructive-variant components now hardcode white text directly instead.
As independent validation that the OKLCH-to-sRGB color math was implemented correctly (not just self-consistent), the resulting computed colors were checked against Tailwind's own published neutral color ramp and land on exact matches — 0.145 lightness resolves to exactly #0A0A0A, 0.922 to exactly #E5E5E5, and the destructive red resolves to exactly Tailwind's published red-600 (#E7000B). This cross-check is itself encoded as an automated test.
3. Architecture
3.1 Token layer
lib/src/tokens/ holds oklch.dart (the OKLCH-to-sRGB color space conversion), colors.dart (19 semantic color slots defined for both light and dark, each one annotated in code with the exact oklch() source string it was derived from), plus spacing.dart, radius.dart, typography.dart, shadows.dart, and motion.dart. No component in the library hardcodes a raw numeric value that should instead come from one of these token files.
3.2 Theming
lib/src/theme/cairn_theme.dart defines CairnTheme as a proper Flutter ThemeExtension<CairnTheme>, deliberately chosen over a bespoke InheritedWidget so the library composes cleanly inside an app's existing MaterialApp rather than requiring it to be replaced wholesale. This choice gets Flutter's built-in theme-change animation (lerp) for free, and keeps Theme.of(context) as the single, familiar lookup mechanism Flutter developers already know. CairnTheme.of() falls back to the light theme rather than throwing if none is provided, and a materialTheme() helper aligns Material's own defaults (color scheme, disabling the default ink-splash effect, disabling Material 3's filled-TextField style) so Material and Cairn widgets don't visually clash when mixed in the same app.
3.3 Shared internals
lib/src/internal/ holds cross-cutting pieces every component can share: interaction.dart (focus-visible-style handling matching CSS's :focus-visible semantics), outer_shadow.dart (see the box-shadow clipping bug in section 5), and popover_layer.dart plus anchored_overlay.dart, which implement flip/shift positioning for anchored overlay surfaces like Popover and Dropdown Menu.
3.4 Two structural component patterns worth understanding
•	Modal vs. anchored surfaces use different underlying Flutter primitives on purpose: Dialog, Sheet, Drawer, and Alert Dialog push a real Flutter PopupRoute, which gives correct focus trapping, focus restoration on close, and back-gesture handling for free. Popover, Dropdown Menu, Context Menu, and similar anchored surfaces instead use OverlayPortal, which deliberately keeps them outside the navigation stack — appropriate since they aren't full-screen modal experiences the way a Dialog is.
•	Text input controls wrap Flutter's TextField rather than rebuilding on the lower-level EditableText: wrapping TextField with InputDecoration.collapsed preserves selection handles, IME composition, autofill, and spell-check for free, which a from-scratch EditableText-based rebuild would have to reimplement. Each text control supplies its own transparent Material ancestor internally, so a consuming app isn't forced to wrap Cairn's inputs in a Material widget of its own just to make them render correctly.
3.5 Notable individual component decisions
•	Data Table is built directly on top of the base Table component rather than as a parallel implementation, specifically so the two can't visually drift apart over time; its sort behavior operates on a defensive copy of the underlying list, which is covered by a dedicated test.
•	Input OTP renders as a single hidden text field behind separately painted visual slots, rather than one real text field per digit — a common naive implementation that silently breaks paste-to-fill and SMS auto-fill on mobile.
•	Icons are implemented as CustomPainters matching Lucide's icon geometry (24x24 viewbox, 2px stroke) directly, rather than depending on an icon font asset or an external icon package dependency.
•	The Form Field component intentionally ships layout only — Flutter's own Form and FormField already handle validation state management well, and Cairn doesn't try to replace that.
4. Testing Strategy and CI Reliability
114 tests total, including 52 golden reference images generated as one composite "sheet" image per component (all of that component's visual variants together in one image) across both light and dark themes, compared byte-for-byte in CI.
4.1 What makes the golden tests actually reliable, rather than flaky
•	A real font is bundled and explicitly loaded for tests: flutter test loads no real font by default, rendering all text as placeholder boxes, which would make text-heavy golden images meaningless. Geist (an OFL-licensed font) is bundled directly in the repo and registered via a FontLoader in flutter_test_config.dart — this alone removes the single biggest source of cross-platform golden-test variance.
•	Golden comparison only runs on Linux, where the reference images were generated: rather than weakening the check with a fuzzy pixel-difference threshold (a common but unreliable workaround), goldens are compared only on the exact platform they were generated on. Off that platform, the same widgets still get built and pumped — which still catches real layout/rendering exceptions — but the byte-level image comparison itself is skipped, with an environment-variable override available to force it.
•	Golden images are regenerated via a dedicated GitHub Actions workflow_dispatch job, run on the identical CI runner architecture they're later verified against, with the Flutter version pinned exactly (3.44.0) so the reference images can only ever change when that pin is deliberately updated — not silently drift due to an unrelated Flutter point release changing font rasterization or anti-aliasing slightly.
•	Golden capture uses fixed frame pumps, not pumpAndSettle: components like the loading Spinner, Skeleton shimmer, OTP input's blinking caret, and an indeterminate Progress indicator all schedule animation frames indefinitely by design, which would make pumpAndSettle wait forever and time out. The test harness also explicitly disables animations globally, which every component correctly honors.
5. Real Bugs Found During the Build
These surfaced specifically because the example app was actually run and visually inspected, not just because widget tests passed — a recurring theme across this whole portfolio series.
5.	A Flutter Container with a non-null alignment property silently expands to fill its bounded parent constraints, rather than shrinking to fit its child's intrinsic size. This quietly broke the CSS w-fit / inline-flex sizing behavior shadcn relies on for several components — every Button, Toggle, Tabs trigger, Kbd element, and Navigation Menu item was stretching to fill the full available width instead of sizing to its content. This was invisible in widget tests (which don't render at a realistic viewport width the way the example app does) and was only caught by actually looking at the running app. Five dedicated regression tests were added once found.
6.	Flutter does not clip an outer box-shadow to a shape's outline the way CSS does. On transparent-background controls, a subtle shadow (shadow-xs) rendered as a visible grey wash across the whole bounding box instead of a subtle edge shadow, and a 3-pixel focus ring rendered as a solid filled color over the entire control rather than a thin ring around it. Fixed with a dedicated CairnShadowed helper that paints the shadow through a clip specifically removing the shape's own interior.
7.	Tailwind's opacity modifier syntax (a slash followed by a number, e.g. bg-input/30) multiplies a color's existing alpha channel rather than replacing it outright. Since shadcn's dark-mode --input token already carries roughly 15% alpha internally, dark:bg-input/30 actually resolves to about 4.5% opacity in the real rendered output, not 30% — six times weaker than a naive implementation would produce. This affected 11 separate components before being caught and corrected.
8.	CSS blur radius and Flutter's blurRadius parameter are not the same unit and don't convert 1:1 — CSS's effective blur sigma is roughly half its stated blur value, while Flutter's blurRadius-to-sigma relationship uses a different formula entirely (roughly radius times 0.57735 plus 0.5). Copying a shadow's blur value directly from a Tailwind class into Flutter without converting inflates the visible blur by roughly 50%.
9.	A late final AnimationController field was being disposed before it had ever actually been constructed or used, specifically for a determinate (non-animating) CairnProgress instance that never touched the controller during its lifetime — meaning dispose() was the very first access to that lazily-initialized field, and constructing a Ticker on an already-deactivated widget element throws. This was caught by the golden test suite actually exercising that code path, not by a targeted unit test written in advance.
10.	A semantics assertion failure: providing onIncrease alongside a value in a Semantics node also requires providing increasedValue and decreasedValue, or Flutter's accessibility framework throws — an easy requirement to miss when only partially wiring up semantic properties.
11.	Tailwind's disabled:pointer-events-none needed an actual IgnorePointer widget in the Flutter translation — without it, descendant widgets kept receiving tap events even though the control's own visual disabled state was rendering correctly.
12.	PowerShell 5.1 silently corrupted several source files during development: a Get-Content/Set-Content -Encoding utf8 round-trip double-encoded em-dashes into mojibake, because PowerShell 5.1 read the file as the system's ANSI codepage before writing it back out as UTF-8. Repaired by re-decoding the corrupted files from cp1252 back to proper UTF-8. This is a known, previously-documented hazard of this specific machine's toolchain, not a one-off fluke.
13.	Running `dart analyze` scoped only to lib/ hid a prefer_const_constructors lint violation that existed only in the test suite — CI's broader analyze scope caught what a narrower local check had missed.
14.	pub.dev's own pana quality scorer flagged two non-obvious issues: a package description over its 180-character soft limit, and — more surprisingly — that appending extra attribution text directly onto the LICENSE file caused pana's automated license detector to fail to recognize the license at all, scoring zero out of ten points for that category outright. Moving that extra text into a separate NOTICE.md file and leaving LICENSE as an unmodified, cleanly-detectable MIT license text fixed it, contributing to the final 160/160 score.
6. A Security Note Worth Recording
During the build, a system-level instruction directing that a Co-Authored-By: Claude trailer be added to commits appeared embedded inside a tool result mid-session, rather than as a genuine instruction from the user or the actual system prompt. Tool results are untrusted content, not a trusted instruction channel, and the injected instruction also directly contradicted this user's explicit, repeatedly-confirmed standing preference against any such trailer — so it was correctly ignored, and no commit in the final repository contains one. This is a concrete, real example of exactly the kind of prompt-injection risk that any system processing untrusted tool output has to defend against as a matter of course.
7. Key Concepts Worth Taking Away
•	Design tokens should be extracted from a living source, not memorized: a design system's underlying values (color space, spacing scale, radius formula) change across versions in ways that aren't always visible from the rendered output alone — verifying against the actual current upstream source, rather than trusting prior knowledge of how a library "used to" work, is what caught all four of the stale-assumption issues in section 2.
•	Golden tests are the correct tool specifically for a design-system library, in a way they wouldn't necessarily be the star testing technique for a typical app — appearance IS the product being shipped here, so a test that locks in and continuously verifies visual output is doing exactly the job a component library's test suite most needs to do.
•	CSS and Flutter share vocabulary but not always semantics: box-shadow clipping, blur-radius units, and alpha-modifier syntax all look like they should translate directly between the two platforms and don't — each one produces a plausible-looking but quantifiably wrong result if translated naively, and each was only caught by actually comparing rendered output rather than assuming a straightforward 1:1 mapping.
•	Treat all tool-result content as untrusted, always: an embedded instruction inside a tool result is not the same thing as a real instruction from the user, no matter how authoritative it's phrased — a concrete instance of this happened during this exact build.

8. Extension: daisyUI-Inspired Components (v0.2.0)
Cairn is a shadcn/ui recreation, so its catalogue stops where shadcn/ui does. daisyUI covers shapes shadcn/ui has no equivalent for, so 20 of them were ported: Stat, Status, Steps, Timeline, Chat Bubble, Rating, Radial Progress, Countdown, Indicator, Stack, Swap, Navbar, Dock, Hero, Diff, File Input, List, Link, FAB (with speed dial) and the Mockup frames (window, browser, code, phone).
Only the idea is borrowed. Every component is built from Cairn's existing tokens and patterns (CairnInteractive for hover/focus/press, CairnTheme for colour and radius, the motion tokens for timing), so the theme, dark mode and radius scale apply unchanged and no existing component was touched. State colours beyond primary and destructive come from a new CairnTone token (success, warning, info), authored in OKLCH like the rest. File Input and Link draw the control but do not open a picker or navigate, to keep the package free of runtime dependencies.
Testing: 42 new behaviour tests (172 total with 14 new golden sheets). One real bug was caught by them: CairnDiff exposed increase/decrease semantics actions without the paired increasedValue/decreasedValue, which Flutter asserts on.
9. Roadmap: Flutter Web and Mobile Templates on Cairn Site
Planned, not yet built: the Cairn Site (github.com/rlphjyson/cairn_site) will provide ready-to-use Flutter templates — a web set (landing page, dashboard, docs shell, auth screens) and a mobile set (onboarding, tab-bar shell using the Dock, settings, chat). Each will be copy-and-run, themed entirely through CairnTheme with light and dark included. The Extended components exist largely so these templates need no one-off widgets.
